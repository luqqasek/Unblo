Model Equality / S82 rule v4

How the heuristics work

The algorithm measures patterns in saved answers, compares those answers with local models, and applies explicit rules to decide which endpoints share the same weights.

A heuristic is an assumption turned into a decision rule. The measurement can be exact while the interpretation is wrong. Repeated wording is measurable; deciding that it means “watermarked base model” is a heuristic.

1The order matters

A family groups endpoints that share the same base model. Within each family, the task asks which endpoints serve the same exact model. A system prompt, sampling change or watermark should preserve model identity; a LoRA weight modification or quantization should change it.

Response-pattern checks first produce tags such as prompt, hot and repeat. Then the labeling code follows this priority:

  1. Strong LoRA evidence? Assign an adapter-and-strength group.
  2. Strong quantization evidence? Assign a quantized-model group, unless a prompt-related tag disables this branch.
  3. Any disguise tag? Join the family’s base-model group.
  4. Unusual fitted temperature? A sufficiently lower value joins the base; a sufficiently higher value remains separate.
  5. Still unresolved? Start with a separate label. A later rule may choose one eligible endpoint as the plain base. Another rule separates colliding undisguised LoRA labels.

The first matching branch wins. A repetition tag does not override strong LoRA evidence, because the LoRA check runs first.

Implementation: v4.py → label().

2Five response-pattern heuristics

These checks look at endpoints within the same family. Several tags can fire for one endpoint. Missing measurements do not count as evidence: unavailable values skip their checks.

Hidden instructions change the answer style prompt

Assumption: an endpoint repeating distinctive, stable instructions may have a custom system prompt rather than different weights.

The probe asks it to repeat the preceding text. The code removes the probe itself, then rejects responses with fewer than 8 words, recognized refusal or boilerplate openings, or too much overlap with the probe. It also rejects text similar to responses from at least two other endpoints, because that could be a shared default template.

Similarity uses Jaccard overlap: shared unique words divided by all unique words in both responses. Overlap with the probe of 0.5 or more is rejected; overlap with a sibling response of 0.6 or more counts as a matching sibling.

# After filtering candidate instruction text:
if any_pair_of_candidates_has_word_overlap_at_least_0_5:
    tags.add("prompt")

One surviving response receives a weaker evidence value of 0.5. The current configuration does not trust that alone; repeated evidence scores 1.0 and triggers the tag.

Observed example: practice endpoint ref-06 receives prompt and repeat. Its known configuration is a watermark. That demonstrates why the tag describes a detected pattern, not a verified deployment mechanism.

Can fail: a model can invent instructions or repeat stable boilerplate. Real hidden instructions may never be disclosed.

The endpoint stops naming its usual maker unnamed

Assumption: a persona or system prompt can suppress the normal model identity.

The code scans “who made you?” responses for known model and vendor names. A name is usual for the family if it appears in at least half of an endpoint’s identity responses for at least max(2, 0.4 × family size) endpoints. It then measures how often each endpoint mentions any of those usual names.

if fraction_naming_a_usual_maker <= 0.25:
    tags.add("unnamed")

Observed example: tb-15 mentions the family’s usual maker in 0% of its identity responses. It receives unnamed, even though its known configuration includes both a LoRA and a system prompt.

This tag has three effects: it supports joining the base later, raises the LoRA threshold from 4 to 15, and disables the quantization-label branch.

Can fail: self-identification can be false, absent or altered by changed weights. The family’s “usual” name is itself inferred from responses, not verified model metadata.

Unusually varied vocabulary suggests hotter sampling hot

Assumption: raising the sampling temperature introduces unusual, less repeatable word choices.

Across the long-writing prompts, the code counts words that occur exactly once for this endpoint and nowhere in its siblings’ answers. Divide by the endpoint’s total word count to obtain h. Let m be the family median of that fraction, and n the number of words. At least 150 words are required.

ratio = h / m
z = (h − m) / sqrt(m × (1 − m) / n)
if ratio >= 1.5 and z >= 4 and not maker_name_suppressed:
    tags.add("hot")

The maker-name gate prevents some persona-like responses from being treated as hotter sampling. Here z is a heuristic standardized difference, not a calibrated confidence level; generated words are not independent observations.

Observed example: tb-05 has a ratio of 2.599 and z = 15.518. Its identity responses pass the maker-name gate. It receives hot, consistent with its known higher-temperature configuration.

Can fail: an adapter, a writing instruction, or different vocabulary coverage can also increase unique words. Short responses may never provide enough evidence.

Repeated openings suggest constrained generation repeat

Assumption: watermarking or colder sampling can make answers to repeated prompts begin the same way.

There are two independent routes to the same tag. For text, compare every pair of responses to each identical writing prompt and count the consecutive matching words from the start. For digits, compare the extracted digit sequences.

RouteAll conditions must pass
Text openingsAt least 3 response pairs; mean matching opening ≥ 6 words; at least 30% of pairs share ≥ 8 opening words.
Digit openingsMean matching opening ≥ 12 digits; ratio to max(family median, 0.5) ≥ 5.
if text_conditions_pass or digit_conditions_pass:
    tags.add("repeat")

Observed example: tb-08 has an average matching digit opening of 111 digits, or 222× the denominator used for its family. That triggers the digit route. Its text openings average 22 words, but there is only one text pair, so the text route does not pass.

Can fail: formatting instructions, predictable prompts, low temperature, or a modified model can all cause repetition. This does not identify a particular watermark.

Skewed random digits suggest token bias skew

Assumption: a watermark can favor particular tokens, shifting the distribution of “random” digits.

The code needs at least 100 extracted digits per endpoint and at least three endpoints with valid histograms. It takes the family median frequency for each digit, then normalizes those ten medians to sum to one. That is the reference distribution.

distance = 0.5 × sum(abs(endpoint_frequency − reference_frequency))
relative = distance / max(family_median_distance, 0.02)
if distance >= 0.15 and relative >= 2.5:
    tags.add("skew")

Observed example: tb-07 has distance 0.279 and relative distance 6.205. Both thresholds pass, producing skew. Its known configuration uses a KGW watermark.

Can fail: language models are not uniform random-number generators. Personas and weight changes can also bias digits, and a biased family reference can hide an effect.

Measurements and tag conditions: typed2.py → features(), types().

3Compare answers against local weights

These checks reuse the answers already collected. They do not ask candidate models to generate matching text. Instead, they calculate the probability that each candidate assigns to the exact observed answer tokens, conditioned on the prompt and earlier answer tokens.

answer log-likelihood = sum(log(probability of each observed token))
gain = best modified-model log-likelihood − best base-model log-likelihood

Log-likelihoods are summed across the selected answers at each temperature. The code then picks the best searched temperature for each candidate. Positive gain favors the modification; negative gain favors the base. Units are nats, meaning natural-log units. A gain of 5 is not 5% confidence.

Known LoRA adapters explain the tokens better

Assumption: if a locally available adapter makes the saved answers sufficiently more likely, that endpoint uses related modified weights.

For each available adapter, the code compares several strengths to strength zero, the base. The default scoring grid uses strengths 0.15, 0.3, 0.5, 0.7, 1.0, 1.5, although some runs use only a subset. Temperature is searched over 0.5, 0.6, 0.7, 0.8, 0.9, 1.0, 1.15, 1.3. The highest-gain adapter/strength wins the comparison.

prompted = "prompt" in tags or "unnamed" in tags
threshold = 15 if prompted else 4

if best_lora_gain >= threshold:
    label = adapter_and_strength_bucket

Strengths are grouped as 0.15/0.3 → weak, 0.5/0.7 → mid, 1.0 → strong, and 1.5 → xstrong. This bucketing is another approximation: different strengths really do change the weights.

Observed near miss: tb-15 has a best LoRA gain of 14.693. Its unnamed tag raises the threshold to 15, so LoRA is not selected. The rule eventually puts this known LoRA endpoint into the base group.

Can fail: the true adapter may be absent from the candidate set. A wrong prompt template, nuisance effect, limited data, or searched candidate can change the gain. Fixed total-gain thresholds also depend on how much text was scored.

Token scoring: wb_score.py. Aggregation: v3.py → lora_gains(). Final thresholds use v4’s settings, not v3’s older classifier.

Reconstructed quantization explains the tokens better

Assumption: rounding the local base model’s weights in a similar way to the server can reproduce useful likelihood differences.

The comparison code can construct per-tensor FP8, grouped FP8, per-row INT8, NF4, and FP4 weight approximations. Each actual run chooses which copies to test. It searches temperatures 0.6, 0.65, 0.7, 0.75, 0.8, 0.9, 1.0, 1.1.

best_copy = copy_with_highest_likelihood_gain
if best_copy.gain >= 5 and not prompted:
    label = "QUANT:" + best_copy.kind

This branch runs only if the LoRA branch did not win. A prompt or unnamed tag disables it, even if the gain exceeds 5.

Observed example: submitted endpoint ep-22 has grouped-FP8 gain +30.695, no prompt-related tag, and no qualifying LoRA fit. The rule assigns QUANT:fp8m. Its true server configuration is unavailable; this is the algorithm’s interpretation.

Can fail: these are weights-only reconstructions. They do not reproduce every server kernel, activation quantization method, scale choice, or deployment setting. Negative gains rule out neither all quantization nor other weight changes.

Reconstruction and scoring: quant_llr.py.

4Finish the model groups

These rules operate on the measurements above. They encode assumptions about which differences should preserve model identity.

A disguise tag joins the base group

# Reached only when LoRA and quantization did not win.
if tags:
    label = "BASE"

Any of the five tags is enough. The intention is to group system prompts, personas, sampling changes and watermarks with their underlying base model.

Can fail: an endpoint can have both a disguise and a LoRA. If the modification check misses the LoRA, this rule wrongly merges it into the base. tb-15 and tb-17 demonstrate that failure.

Fitted temperature separates cold and hot-looking endpoints

For untagged endpoints with quantization evidence, the code takes the lower median of their fitted base temperatures as the family reference T₀. With an even count, the lower of the two middle values is used, rather than their average.

if fitted_T <= T0 - 0.08:
    label = "BASE"
elif fitted_T >= T0 + 0.08:
    label = endpoint_id

A lower fitted temperature is treated as colder sampling of the base. A higher value is treated as an unexplained variant. This is asymmetric, and it is different from the earlier vocabulary-based hot tag: a tag already joins the base before this branch is reached.

Observed failure: tb-39 has fitted temperature 0.80 against a family reference of 0.70. It stays separate. Its known configuration is a KGW watermark on unchanged base weights.

Can fail: the best-fitting temperature can absorb watermarking, prompt mismatch or changed weights. It is not a direct reading of the server’s actual temperature.

Unresolved endpoints begin with separate labels

label = endpoint_id

If no earlier check establishes a group, the endpoint initially stands alone. This reduces unsupported merges, at the cost of splitting genuine copies.

Observed failure: tb-09 remains separate from the base even though it is the base with a TextSeal watermark. “Separate” means the rules did not establish a match; it is not proof of different weights.

Choose one eligible endpoint as the plain base

Only unresolved, plain-looking endpoints with quantization/temperature evidence are eligible. Among these, the rule picks the lowest fitted temperature, then breaks ties using the most negative minimum reconstructed-copy gain per token. Exactly one eligible candidate is added to BASE; other members may already have joined through earlier rules.

key = (
    fitted_temperature,
    min(copy_gains) / number_of_scored_tokens
)
plain_base = candidate_with_smallest_key

The use of min is literal: this tie-breaker uses the worst-fitting tested copy, whereas quantization detection uses the best-fitting copy.

Observed failure: the rule selects tb-31 as a Qwen-3B base candidate. Its known configuration is a maths LoRA. The available test-bed likelihood comparisons include the persona adapter, but not the maths adapter.

Can fail: no plain base may be among the eligible candidates. A modified endpoint can win a relative ranking without being a true base model.

Separate colliding undisguised adapter buckets

If two untagged endpoints land in the same adapter/strength bucket, the endpoint with the higher gain keeps that bucket label; the other gets an endpoint-specific suffix. Tagged endpoints are not split by this collision rule. This adjustment runs after the initial branches and before plain-base selection.

Assumption: two undisguised endpoints are not duplicate deployments of the same configuration; the coarse bucket must be hiding distinct strengths.

Observed example: ep-11 qualifies for LORA:general:strong with gain 9.096, but a stronger-gain untagged endpoint already occupies that bucket. Its saved label becomes LORA:general:strong:ep-11.

Can fail: if the assumption about duplicate configurations is wrong, this rule forces a false split.

Grouping, priority and tie-breaking: v4.py.

5What the code verifies

A complete example: why tb-15 fails

  1. Detect a pattern. It never names the family’s usual maker, so it gets unnamed.
  2. Check LoRA. The best gain is 14.693. Because it is tagged as prompted, it needs at least 15. The check fails.
  3. Check quantization. The unnamed tag disables this branch. Its best copy gain is negative anyway.
  4. Apply the disguise rule. A tag exists, so the endpoint joins BASE.
  5. Compare with known truth. It is actually LoRA strength 0.7 plus a system prompt. It should match tb-12. The result produces 10 false merges and 1 false split involving tb-15.

The code followed its rules correctly. The assumptions and threshold led to an incorrect model grouping.

Group correctness is checked pair by pair

For every pair inside a known family, the benchmark compares two statements:

predicted_same = prediction[a] == prediction[b]
actually_same  = truth[a] == truth[b]
correct       = predicted_same == actually_same

A false merge predicts “same” when the true models differ. A false split predicts “different” when the true model is the same. The counts feed Matthews correlation coefficient (MCC), which is not percentage accuracy.

The submitted workflow also contains manual inputs

The local benchmark computes the response tags described above. The submission script instead reads a saved family map and hand-entered disguise tags. It also explicitly excludes ep-26 from plain-base selection because an earlier public submission merging it into the base lowered the public score.

That public-score feedback is part of how the final submission was constructed. It is separate from automatic feature measurement and from independent validation. The saved public score of 1.00 does not reveal endpoint-level truth or the final held-out result.

Passing the benchmark checks validates the final pair decisions on those saved examples. It does not prove that a tag identifies the true disguise, that the thresholds are calibrated, or that the rules generalize to unseen model families.
